# Архитектура SHUZU

Один и тот же интерфейс и одна и та же логика работы с подписками живут в `src/` и `shared/`.
Различается только «нижний этаж» — то, что умеет запускать ядро и лезть в сеть в обход браузера.

```
┌──────────────────────────────────────────────────────────────────────┐
│ renderer: React 18 + framer-motion (src/)                            │
│   экраны, world map, кнопка питания, списки, модальные окна          │
│   обращается к миру только через window.shuzu : ShuzuApi             │
└───────────────┬──────────────────────────────────────────────────────┘
                │  (IPC через preload / Capacitor Bridge)
    ┌───────────┴────────────┐
    │                        │
┌───┴──────────────────┐  ┌──┴──────────────────────────────────────────┐
│ Electron main        │  │ Android: Capacitor + Java                   │
│  electron/main.ts    │  │  ShuzuPlugin (мост)                         │
│  core.ts   — ядро    │  │  ShuzuVpnService (VpnService + плашка)      │
│  net.ts    — пинги   │  │  CoreRunner (запуск sing-box)               │
│  diagnostics.ts      │  │  hev-socks5-tunnel (JNI, tun2socks)         │
│  censor.ts           │  │                                             │
│  updater.ts          │  │                                             │
└───┬──────────────────┘  └──┬──────────────────────────────────────────┘
    │ sing-box.exe + wintun   │ libsingbox_<abi>.so + libhev-socks5-tunnel.so
    └───────────┬─────────────┘
                │
        общий TypeScript (shared/): разбор ссылок, генерация конфига,
        оценка качества серверов, отчёты диагностики и блокировок
```

## Почему sing-box

Одно ядро на обе платформы, статический бинарник, поддержка всего, что реально встречается
в подписках: VLESS + Reality, VMess, Trojan, Shadowsocks, Hysteria2, TUIC, транспорты
ws/grpc/http/httpupgrade, uTLS-отпечатки. Плюс Clash API: через него считаются пинги через
туннель, трафик и текущее соединение.

## Windows

1. Ядро лежит в `resources/core/sing-box.exe` (+`wintun.dll`), копируется в `%APPDATA%` при первом
   запуске — антивирусы спокойнее относятся к запуску из пользовательского каталога, а обновление
   приложения не ломает работающий процесс.
2. Конфиг генерируется на каждый запуск: `shared/singbox.ts` → JSON → временный файл.
3. Режим **TUN**: sing-box создаёт адаптер Wintun и забирает маршруты (`auto_route`, `strict_route`).
   Требует прав администратора — Wintun ставит драйвер только с повышением.
4. Режим **системного прокси**: sing-box поднимает `mixed`-порт (HTTP+SOCKS), приложение
   прописывает его в настройки прокси Windows через реестр и снимает при выходе.
5. Состояние читается из Clash API (`/connections`, `/proxies`) — отсюда живой трафик и пинг
   через туннель, без парсинга логов.

## Android

```
приложения → TUN (VpnService) → hev-socks5-tunnel → 127.0.0.1:10808 (sing-box socks) → сервер
```

- `ShuzuVpnService` создаёт TUN (`172.19.0.1/30` + IPv6, MTU 1500, DNS 1.1.1.1/8.8.8.8).
- `CoreRunner` запускает ядро из `nativeLibraryDir` — единственное место, откуда Android
  разрешает исполнять файлы в APK. Поэтому бинарник упакован как `libsingbox_arm64.so`.
- Трафик самого приложения исключён (`addDisallowedApplication`), иначе SOCKS-соединение
  к ядру ушло бы в тот же туннель и получилась петля.
- Плашка — foreground-служба с `RemoteViews` в стиле приложения: имя сервера, пинг, «Отключить».
  На Android 14 указан тип `specialUse` с подтипом `vpn` — без него система убивает службу.
- Статистика трафика — из JNI (`TProxyGetStats`), состояние — из статических полей службы,
  которые читает плагин. WebView никогда не опрашивает систему напрямую.

## Генерация конфига

`buildSingboxConfig()` собирает:

| Часть | Что делает |
|---|---|
| `inbounds` | TUN (ПК) или SOCKS (Android, tun2socks) или `mixed` (системный прокси) |
| `outbounds` | по одному на сервер (`srv-<hash>`), `auto` (`urltest`), `proxy` (`selector`), `direct`, `block` |
| `route.rules` | sniff → блок рекламы → белые списки РФ → локальная сеть → hijack-dns |
| `dns` | DoH через туннель, обычный DNS через direct, final — по настройке |
| `experimental` | Clash API на 127.0.0.1 со случайным секретом, кэш для быстрого старта |

Идентификаторы серверов стабильны (хеш от ссылки), поэтому избранное и выбранный сервер
не теряются при обновлении подписки.

## Диагностика

Windows-часть (`electron/diagnostics.ts`) проверяет то, что нельзя проверить из браузера:
наличие ядра, версию, Wintun, права, попытки запуска TUN из лога, брандмауэр, hosts,
чужие VPN-адаптеры, таблицу маршрутов, MTU, системный прокси, антивирус, время.

Каждая проверка возвращает `{ id, title, group, weight, status, detail, fix }`. `buildReport()`
считает взвешенный балл (0–100) и вердикт: `healthy` / `degraded` / `blocked` / `unknown`.
Список `fix` превращается в кнопки — приложение не просто говорит «плохо», а предлагает действие.

## Проверка блокировок

`shared/censor.ts` + `shared/rules.ts`: 19 целей в группах `local`, `global`, `media`,
`messenger`, `cloud`. Для каждой — DNS, TCP-хендшейк и HTTPS-запрос. Вердикт:

- всё открыто → фильтрации нет (`open`);
- локальные открыты, глобальные нет → фильтрация (`filtered`), балл DPI высокий;
- не открывается ничего → это не DPI, а отсутствие интернета (`unknown`).

Дополнительно фиксируются «подозрительные» цели: TCP проходит, HTTPS — нет (классика
TLS-блокировки), и подменённые DNS-ответы.
